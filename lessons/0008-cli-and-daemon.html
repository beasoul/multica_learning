Lesson 08

CLI 与 daemon：一个二进制，两副面孔

第 1 课留下的那个疑点现在来解：为什么 .gitignore 里既有 server/daemon 又有 server/multica？答案是它们本来就是同一个程序。这一课顺便把 CLI 变成你的脚本化入口。

约 35 分钟 对应源码：server/cmd/multica/ · internal/cli/ · CLI_AND_DAEMON.md 前置：第 7 课（daemon）

一、证据先摆出来

CLI_AND_DAEMON.md 的第一句话就是答案：

源码原话

The multica CLI connects your local machine to Multica. It handles authentication, workspace management, issue tracking, and runs the agent daemon that executes AI tasks locally.

一个程序，两种用法：

用法命令形态生命周期
交互式 CLImultica issue list、multica login跑完即退
常驻 daemonmultica daemon start后台长期存活

这也解释了 .gitignore 里那几行看似重复的忽略项——它们是同一个 Go 二进制在不同构建产物路径下的名字。

关键事实

代码位置：server/cmd/multica/。里面有一批 cmd_*.go 文件，每个对应一族子命令（cmd_issue.go、cmd_workspace.go……），daemon 相关逻辑则在 server/internal/daemon/。

所以你在第 7 课读的 daemon 源码，和你会敲的 multica 命令，是同一个程序的两半。

二、最短上手路径

# 一条命令搞定：写配置 + 浏览器登录 + 起 daemon
multica setup            # 连官方云
multica setup self-host  # 连自部署

# 或者拆开来做
multica login                     # 浏览器 OAuth，生成 90 天 PAT，自动加入你的工作区
multica daemon start              # 后台起 daemon
multica daemon status             # 看 PID、运行时长、检测到的 Agent、监听的工作区

multica login 有个省事的副作用：它会自动发现你所属的全部工作区，并加进 daemon 的监听列表。所以第一次跑完通常不需要额外配置。

无头环境（CI、服务器）用令牌登录：

multica login --token <mul_...>
multica login --token=          # 交互式输入，令牌不进 shell 历史

三、daemon 的日常操作命令

命令用途备注
multica daemon start起后台 daemon--foreground 前台跑，方便调试
multica daemon stop停 daemon退出时会注销全部 Runtime
multica daemon status看状态--output json 便于脚本
multica daemon logs -f看日志并跟踪先打印它解析出的绝对路径，避免看错 profile
multica daemon disk-usage看磁盘占用.repos 单独一行，不摊到各任务里
小心

"我的日志怎么是旧的？"——这是最常见的自伤。daemon 日志落在它启动时那个 profile 的状态目录里，默认 ~/.multica/，带 --profile 时是 ~/.multica/profiles/<name>/。桌面端用的是它自己的命名 profile。

所以同一台机器上可能存在两份看起来都合理的 daemon.log，但只有一份在被写。multica daemon logs 每次都会打印它读的绝对路径——看那一行，别猜。

四、Profiles：一台机器跑多个 daemon

Profile 是彻底隔离的单位：各自的配置目录、daemon 状态、健康检查端口、工作区根目录。

# 生产用默认 profile，staging 用命名 profile
multica setup self-host --profile staging --server-url https://api-staging.example.com
multica daemon start --profile staging
multica daemon status --profile staging     # 后续命令都要带上 --profile
类比

Profile ≈ Oracle 里给同一个客户端机器配多套 TNS_ADMIN 与 tnsnames.ora：一个连生产库，一个连测试库，凭据与默认目标互不干扰。

区别是这里连daemon 进程和端口都分开，所以可以同时活着。

五、命令怎么知道"操作哪个工作区"

每条命令只作用于一个工作区，解析优先级（从高到低）：

  1. 命令上的 --workspace-id <id> 参数
  2. 环境变量 MULTICA_WORKSPACE_ID
  3. 当前 profile 里存的默认工作区（由 multica login 或 workspace switch 写入）

写脚本时推荐用前两种——不留隐式状态，行为可复现。multica config set workspace_id 是低层写法，它会跳过权限检查直接写，所以日常切换用 workspace switch（先校验可访问再保存）。

六、脚本化实战：一条命令链

这是 MISSION 里"用脚本而不是手点界面"的具体形态：

# 1. 建一个 Issue 并直接指派给某个 Agent
multica issue create --title "修复登录页闪烁" \
  --description "复现步骤见附件" \
  --priority high --assignee "Lambda"

# 2. 拿它的 KEY（形如 MUL-123）跟进后续操作
multica issue list --status todo --assignee "Lambda" --output json

# 3. 看这条 Issue 的全部执行记录
multica issue runs MUL-123

# 4. 只看还在跑的（queued / dispatched / running / waiting_local_directory）
multica issue runs MUL-123 --active --output json

# 5. 看某一次 Run 的详细消息流（工具调用、思考、错误）
multica issue run-messages <task-id> --since 42 --output json

# 6. 看这条 Issue 累计消耗
multica issue usage MUL-123 --output json
关键事实

--active 这个开关就是第 5 课状态机的直接应用：它把"非终态"翻译成一句人能读懂的问题——"现在有 Agent 正在干这件事吗？"

源码里的原话是 Instead of the full execution history. Answers "is an agent working on this right now"。

七、脚本友好性：JSON、退出码、调试开关

能力用法
结构化输出--output json（列表类默认 table）
字段裁剪--fields=id,title,status,priority（仅 JSON）
退出码分层0 成功／1 未分类／2 网络／3 认证授权／4 未找到／5 校验失败
原始错误链--debug 或 MULTICA_DEBUG=1
请求超时MULTICA_HTTP_TIMEOUT=60s（默认 30 秒）
中文报错检测到中文 locale 自动切换，无需参数

退出码分层值得多看一眼，因为它让你能写出有分支的脚本：

multica issue get MUL-9999
case $? in
  0) echo "找到"; ;;
  4) echo "这条 Issue 不存在，走建单流程"; ;;
  3) echo "令牌过期了，需要重新 login"; ;;
  2) echo "网络问题，稍后重试"; ;;
esac

另外，CLI 把错误收敛在一个专门的翻译层里——源码是 server/internal/cli/errors.go。它的承诺是：默认只给你一句能照做的话，不泄漏 URL、状态行和内部调用链；需要细节时再加 --debug。

八、换了二进制会怎样（自动重载）

这是个容易被忽略但很实用的机制：CLI 启动的 daemon 会周期性比对自己的编译版本与"如果重新 exec 会启动的那个 multica 二进制"的 --version。不一致时（比如你跑了 brew upgrade multica、或本地 make build）：

  1. 等正在跑的任务结束——绝不中断运行中的任务；
  2. 然后重启进新二进制。

如果 daemon 正忙，重启就推迟到下一次检查，multica daemon status 会说明它为什么还在旧版本上。想关掉这个行为：

MULTICA_DAEMON_AUTO_RELOAD=0 multica daemon start
multica daemon start --no-auto-reload
multica config set disable_auto_reload true
小心

两件容易混的事：「跟随二进制替换」与「向 GitHub 查询更新」是独立的两个机制。关掉自更新轮询，不会阻止 daemon 跟随你自己装的二进制。

而 Agent CLI（claude、codex……）被就地升级时，处理方式又不同：daemon 会重新探测版本并重注册 Runtime，不重启自身——这样 Multica 的可用性就不取决于第三方 CLI 的发版节奏。

不看上文，写出 CLI 决定"操作哪个工作区"的三级优先级，并说明脚本里为什么偏向用前两级。

  1. --workspace-id <id> 命令参数（最高优先级）
  2. MULTICA_WORKSPACE_ID 环境变量
  3. 当前 profile 中保存的默认工作区（由 login 或 workspace switch 写入）

脚本里偏向前两级，因为它们是调用时显式给出的：不依赖某个配置文件里存着什么，换机器、换 profile 行为都一样。第三级是隐式状态，人和脚本共用时会互相污染。
