Lesson 06

一次 Run 的端到端时序与凭据链

上一课讲"状态怎么变"，这一课讲"谁在什么时候推它变"。重点是那条从你的会话一路收窄到单次运行的凭据链——这是整个系统安全模型的核心，也是它敢把 Agent 跑在你机器上的前提。

约 40 分钟 对应图表：04 一次 Run 端到端时序 对应源码：server/internal/auth/jwt.go · pkg/db/queries/task_token.sql · internal/daemon/daemon.go

一、把状态机摊平成时间线

参与者只有四个：你（客户端）、服务端、daemon、Agent CLI。整个流程是：

#谁 → 谁发生了什么状态变化
1你 → 服务端把 Issue 指派给某个 Agent/Squad— → queued
2服务端 → daemon通过 daemon 的 WebSocket 通道告知"你这个工作区有活"—
3daemon → 服务端POST /api/daemon/tasks/claim 认领；服务端签发一枚 mat_ 令牌queued → dispatched
4daemon（本机）解析 Agent 配置 → 找到对应 Runtime/CLI 路径 → 准备本地工作目录可能 → waiting_local_directory
5daemon → 服务端POST .../start 声明开始dispatched → running
6daemon → 本机spawn Agent CLI 进程，把 mat_ 令牌通过环境变量注入—
7CLI → 服务端（或经 daemon 转发）持续上报进度、消息、用量不改状态
8daemon → 服务端POST .../complete 或 .../failrunning → 终态
9服务端 → 你写 Run 记录 + 推 Inbox 通知 + 广播实时事件—

二、四种令牌：一条逐级收窄的链

Multica 有四种凭据，前缀各不相同。认前缀就能判断手上这串字符串"是什么身份"：

令牌前缀代表谁能做什么
会话 JWT（Cookie multica_auth）你，在浏览器里全量 Web API
个人访问令牌 PATmul_ + 40 位十六进制你，在脚本/CLI 里与你的会话同等权限，但有独立生命周期
daemon 令牌mdt_ + 40 位十六进制你机器上的 daemon 进程只能进 /api/daemon/* 那一组接口
运行令牌mat_ + 40 位十六进制某一次具体的 Run只够汇报这一条 Run 的进度/消息/用量
源码原话

GenerateAgentTaskToken creates a new task-scoped agent auth token: "mat_" + 40 random hex chars. The token is single-purpose — bound to a specific (agent_id, task_id) pair on the server side — and is what the daemon injects into the agent process in place of its own owner PAT.（server/internal/auth/jwt.go）

最后一句是全部重点：daemon 不把自己那把"owner PAT"交给 Agent，而是换成一枚只能干这一件事的 mat_。

它怎么做到"只能干这一件事"

机制实现
绑定范围入库时同时写死 task_id、agent_id、workspace_id、user_id
不存明文表里存的是 token_hash（SHA-256），数据库泄露也拿不到可用令牌
自动过期带 expires_at，校验和清理都按时间过滤（expires_at > now()）
用完即弃Run 结束后按 task 删除令牌（DeleteTaskTokensByTask）
 
-- server/pkg/db/queries/task_token.sql
-- name: CreateTaskToken :one
INSERT INTO task_token (token_hash, task_id, agent_id, workspace_id, user_id, expires_at, id) ...

-- name: GetTaskTokenByHash :one
... WHERE token_hash = $1 AND expires_at > now();

-- name: DeleteTaskTokensByTask :exec
-- name: DeleteExpiredTaskTokens :exec
DELETE FROM task_token WHERE expires_at <= now();
关键事实

这条链的每一步权限都在收窄：你的会话（全量）→ daemon 令牌（只能调 daemon 接口）→ 运行令牌（只能汇报这一条 Run）。

这就是为什么"让 AI 自己改你的代码"这件事在工程上可接受：即使 Agent 被提示注入攻击、行为失控，它手上也只有一枚一天内失效、只够报告进度的令牌。

三、注入给 Agent 的运行环境

daemon spawn CLI 时，会注入一组环境变量。源码里是一张明表：

func taskMulticaEnvironment(task Task, agentName, token, configRoot, workspacesRoot, serverURL string, ...) map[string]string {
	return map[string]string{
		"MULTICA_TOKEN":        token,        // ← 就是那枚 mat_ 运行令牌
		"MULTICA_SERVER_URL":   serverURL,
		"MULTICA_WORKSPACE_ID": task.WorkspaceID,
		"MULTICA_AGENT_ID":     task.AgentID,
		"MULTICA_AGENT_NAME":   agentName,
		"MULTICA_TASK_ID":      task.ID,
		"MULTICA_TASK_SLOT":    strconv.Itoa(slot),
		"MULTICA_DAEMON_PORT":  strconv.Itoa(healthPort),
		...
	}
}

（server/internal/daemon/daemon.go）

两个细节值得记住：

  • MULTICA_TASK_ID 是 Agent CLI 知道"我在为哪条 Run 干活"的唯一方式。你在 Agent 里写的脚本想上报进度，就靠它。
  • MULTICA_TASK_SLOT：同一台机器上可以并行跑多条 Run，slot 是并发槽位编号。这解释了你在一台机上能看到多个 Agent 同时工作。
小心

daemon 会校验服务端发回来的令牌确实是 task 级的，不是就报错：源码里那句 errors.New("server provided non-task-scoped auth token") 就是这道闸门。

它是防止"服务端配置退化导致 daemon 把高权限令牌传进不可信的 Agent 进程"的最后一道防线。

四、这条链和"普通做法"的差别

类比

Oracle 里有个常见做法：应用连库用一套 APP_USER，权限很大，所有业务都借它的身份执行。只要应用有注入漏洞，攻击者就等于拿到了 APP_USER。

Multica 的选择相当于每次都换成一次性角色：进门前先 SET ROLE 到一个只能操作这一行记录的角色。代价是每跑一次要签一次令牌，收益是攻击面被压到最小。

更接近的对照是：PAT ≈ 长期 API Key；daemon 令牌 ≈ 服务账号；mat_ ≈ 一次性委托票据（类似 OAuth 的 token exchange）。

五、时序里的两个"异步点"

这张时序图里有两处不是同步调用，理解它们能避免很多误判：

  1. 第 2 步（唤醒）是异步通知：服务端不是"命令"daemon 去干活，而是告诉它"有活了"。daemon 可能正在忙别的 Run，也可能没收到——所以 daemon 必须自己会主动查询（第 7 课的轮询循环）。
  2. 第 7 步（进度）是持续流：一条 Run 可以上报成百上千条消息。它们的到达顺序不保证，前端靠事件 + 重查来收敛。
关键事实

数据库才是事实源，WebSocket 只是加速器。这是全仓库反复出现的一句话。丢了任何一条实时事件，客户端靠重新查询都能恢复正确状态；反过来不成立。

令牌前缀范围
