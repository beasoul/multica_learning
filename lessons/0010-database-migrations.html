Lesson 10

数据库与迁移：用 Oracle 的眼睛读 PostgreSQL 工程

这是你的主场。Multica 的迁移规则写得比大多数项目都严格，而且它的很多约束在 Oracle 里有直接对应物——你用 ONLINE 索引重建、DBMS_STATS、advisory lock 这些概念去理解，会比从零学 PostgreSQL 快得多。

约 45 分钟 对应源码：AGENTS.md（Database and Migration Rules）· server/migrations/ · cmd/migrate/README.md

一、先看规模

项现状
迁移文件总数1178 个 = 589 组 .up.sql / .down.sql 成对
命名001_init.up.sql、002_agent_config.up.sql…… 三位编号 + 下划线描述
位置server/migrations/
runnerserver/cmd/migrate/main.go + server/internal/migrations/migrations.go
数据访问server/pkg/db/queries/（65 个 .sql，第 4 课讲过）
关键事实

DDL 与 DML 是分开的两套东西。migrations/ 只管表结构变更（CREATE/ALTER/DROP INDEX），queries/ 只管数据读写。

改表结构 → 动 migrations；改查询 → 动 queries 并重新生成 sqlc。混了就要出问题。

二、三条硬规则（原文照抄）

AGENTS.md 的 Database and Migration Rules 只有三条，但每条都有明确代价：

规则 1：不用外键，也不做级联删除/更新

源码原话

Do not add foreign keys, cascading deletes, or cascading updates. Validate relationships and clean up dependents in application code, using a transaction when the operation must be atomic.

实践含义：引用完整性由应用层负责。删一个工作区时，所有从属数据的清理要显式写出来，必要时包在一个事务里。

类比

这和你在 Oracle 里见到的两种风格之争是同一件事：

  • 把约束交给数据库（外键 + ON DELETE CASCADE）：省心，但一次误删可能连带删掉一大片，而且级联路径不透明。
  • 把约束交给应用：清理逻辑可见、可审计、可分批；代价是每一处新人手都要记得写。

Multica 选后者。你在 queries/workspace_delete.sql 这种文件里看到的就是前者的替代品。

规则 2：所有索引都用 CONCURRENTLY 建

源码原话

Every migration-created index, including indexes on new tables, uses CREATE [UNIQUE] INDEX CONCURRENTLY. Each concurrent index build gets its own single-statement migration file; the runner executes files outside an explicit transaction.

拆成三个可执行的要求：

  1. 建索引一律带 CONCURRENTLY——不长时间阻塞写入。
  2. 每个并发索引独占一个只含一条语句的迁移文件——因为它必须单独执行。
  3. 这些文件由 runner 在事务之外执行——因为 CONCURRENTLY 不能在事务块里跑。
类比

第 1 条你太熟悉了：这就是 Oracle 的 CREATE INDEX ... ONLINE（在线索引重建）。普通建索引会长时间持锁，业务写入被卡住；ONLINE / CONCURRENTLY 都是用更长的构建时间换"不挡业务"。

第 3 条是 PostgreSQL 特有的坑：Oracle 的 DDL 隐式提交，压根不存在"DDL 包在事务里"这种情况；而 PostgreSQL 支持事务型 DDL，于是"并发索引必须在事务外"变成了一条必须显式说明的约束。

规则 3：被跳过的迁移也要记账，后续 DDL 必须幂等

源码原话

Conditionally skipped migrations are still recorded in schema_migrations. Later DDL touching conditional objects must be idempotent (IF EXISTS / IF NOT EXISTS); document recovery if the missing object would break runtime behavior.

这条解释了 cmd/migrate/README.md 里那段很长的说明：有些迁移依赖扩展或操作符类（比如 pg_bigm 的 gin_bigm_ops）。装了就建索引，没装就把 SQL 跳过、但版本号照样记进 schema_migrations。

小心

这个"记账"是永久的。README 里写得很直白：That record is permanent, so a database that gains pg_bigm later never builds the index on its own.

后果：后来才装上扩展的库，索引永远不会自动出现，得手工补建。这个坑和 Oracle 里"条件执行的 DDL 脚本留下不一致状态"是同一类问题。

三、一个完整的性能故事：表达式索引 + 统计信息

README 里有一段堪称教科书的说明，值得逐字理解，因为它同时覆盖了三件容易错的事。场景是给 Issue 的属性（JSONB 文本）做模糊搜索的预过滤索引：

CREATE EXTENSION IF NOT EXISTS pg_bigm;
DROP INDEX CONCURRENTLY IF EXISTS idx_issue_properties_bigm;
CREATE INDEX CONCURRENTLY idx_issue_properties_bigm
    ON issue USING gin (LOWER(properties::text) gin_bigm_ops);
ANALYZE issue;

三条要点：

要点含义Oracle 对照
ANALYZE 不是形式主义 建表达式索引不会自动为表达式收集统计信息。没有统计信息，优化器只能用一个"单字符搜索词约占表 5%"的启发式估算，然后放弃索引走全表扫描——索引建好了、有效、却完全不被使用。 DBMS_STATS.GATHER_TABLE_STATS。同样是"索引存在但优化器不选它"。
表达式要一字不差 谓词写的是 LOWER(properties::text) LIKE LOWER(...)，所以索引也必须是 LOWER 形式。写成 ILIKE 形状或忘了 LOWER，这个索引永远不会被用。 函数索引必须与查询表达式匹配，否则失效。
验证统计真的落库 SELECT count(*) FROM pg_statistic WHERE starelid = 'idx_issue_properties_bigm'::regclass; 查 USER_/DBA_TAB_STATISTICS。
关键事实

这段说明之所以值钱，是因为它把"性能问题可能出在统计信息而不是索引设计"讲成了可复现的步骤。索引存在 ≠ 索引被使用——诊断顺序应该是：看执行计划 → 看有没有统计 → 再看索引定义是否与谓词匹配。

四、检索全文用的是什么

从迁移史能看出一个技术演进：项目早期用 GIN 索引（pg_trgm 三元组 / pg_bigm 二元组）做 Issue 描述与评论内容的全文检索，后来把这两个全局 GIN 索引退役了（迁移 454/455 退役评论内容索引，463/464 退役描述索引）。

源码原话

SearchIssues now scans the selected workspace's issue candidates and evaluates description matches during projection, so neither global description GIN is read.

新的策略是"先按工作区收窄候选集，再在投影阶段做匹配"。这个取舍很好理解：全局 GIN 在大表上又大又难维护，而实际查询永远带着 workspace_id 这个高选择性条件——先用它把范围砍下来，再逐行判断，往往更划算。

为什么是 pg_bigm（二元组）而不是 pg_trgm（三元组）？因为 中文没有词间空格：二元组对 CJK 更友好。这在 README 里也点明了（CJK-friendly bigram index）。

五、迁移在什么时候跑

关键事实：迁移在后端启动过程中执行，不是靠人手动跑的独立步骤。README 提到 Helm 的启动探针给了 10 分钟预算，所以大表上的索引构建要提前评估。

随之而来的操作纪律（README 给的处方，可以照抄）：

  1. 先量规模：SELECT count(*) FROM agent_task_queue WHERE chat_session_id IS NOT NULL;
  2. 低峰窗口预建：把语句单独、事务外跑一遍，让迁移变成快速空操作。
  3. 验证可用性：查 pg_index 的 indisvalid / indisready / indislive 三个标志。
  4. 构建被打断怎么办：并发的无效索引要先 DROP INDEX CONCURRENTLY 再重建；迁移 runner 也注册了无效索引清理，下次启动能自愈。
类比

这套"先预建、再让迁移变成空操作"的做法，在 Oracle 里就是大表上做在线索引重建的标准姿势：别让上线那一刻的 DDL 承担几个小时的构建时间，提前在低峰期把结构准备好，发布时只做一次轻量校验。

六、实操：自己加一个迁移

# 1. 在 server/migrations/ 下按编号新建一对文件
server/migrations/564_add_issue_pinned_at.up.sql
server/migrations/564_add_issue_pinned_at.down.sql

# up：加列（普通 DDL，可幂等时加 IF NOT EXISTS）
ALTER TABLE issue ADD COLUMN IF NOT EXISTS pinned_at timestamptz;

# 若要建索引：单独一个迁移文件，只放一条语句
# server/migrations/565_add_issue_pinned_at_index.up.sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_issue_pinned_at ON issue (pinned_at);

# 2. 改了 SQL 查询就重新生成 sqlc
make sqlc

# 3. 起环境验证
make up && make status

注意三个"不要"：不要加外键、不要在 up 里塞多条语句混着并发索引、不要忘了同步写 down。

七、检索练习

1. 为什么每个 CONCURRENTLY 建索引的迁移都要单独一个文件？

2. 索引建好了、indisvalid 也是真，但查询仍走全表扫描。最可能缺了什么？

3. 一台自部署库最初没装 pg_bigm，半年后装上了。会发生什么？

不看上文，凭记忆写出迁移规则的三条，并各给一个 Oracle 对照。

  1. 不加外键与级联，关系与应用层清理、必要时用事务。
    对照：Oracle 里"约束交给数据库 vs 交给应用"的取舍；这里等同自己写 workspace_delete.sql 这类清理。
  2. 索引一律 CONCURRENTLY，每个并发索引独占一个单语句文件，runner 在事务外执行。
    对照：Oracle 的 CREATE INDEX ... ONLINE；而"必须事务外"是 PostgreSQL 事务型 DDL 带来的额外约束（Oracle DDL 隐式提交，不存在此问题）。
  3. 条件跳过的迁移也记账，后续 DDL 必须幂等（IF EXISTS / IF NOT EXISTS）。
    对照：类似 Oracle 里带条件的 DDL 脚本留下的状态不一致，必须靠幂等重跑自愈。

附加一条操作层面的：迁移在后端启动时执行，所以大表上的索引构建要提前在低峰期预建，让迁移退化为空操作。
