Lesson 04

一个 HTTP 请求的旅行：从路由到 SQL

这一课要给你一个可以反复使用的"读代码套路"：随便挑一个接口，顺着 router → middleware → handler → service → SQL 一路读下去。练熟之后，Multica 后端 130 个 handler 文件对你就不再是黑箱。

约 40 分钟 对应源码：server/cmd/server/router.go · internal/middleware/ · internal/handler/ · internal/service/ 前置：第 3 课（分层）

一、先看总入口

后端的可执行入口在 server/cmd/server/。它做完配置、连接池、迁移之后，最后一步是装配路由——所有 HTTP 接口都写在 router.go 这一个文件里（约 2000 行，但结构极其规整）。

关键事实

server/cmd/server/router.go 是找接口的唯一入口。你想知道"这个功能有没有后端接口、叫什么路径、走哪层鉴权"，永远从这里开始，而不是靠全局搜索。

二、全局中间件链：每个请求都要过一遍

router.go 开头挂了一串全局中间件，顺序就是执行顺序：

r.Use(chimw.RequestID)                    // 1. 给请求打一个唯一 ID，贯穿日志
r.Use(middleware.ClientMetadata)          // 2. 采集客户端信息（UA / IP / 来源）
r.Use(middleware.RequestLogger)           // 3. 记一条访问日志
r.Use(opts.HTTPMetrics.Middleware)        // 4. 若有指标采集器，计入 QPS/耗时
r.Use(chimw.Recoverer)                    // 5. panic 兜底，转成 500 而不是进程崩溃
r.Use(h.PluginSurfaceHostBoundary)        // 6. 插件宿主边界（第 13 课）
r.Use(middleware.ContentSecurityPolicy)   // 7. 安全响应头
r.Use(cors.Handler(...))                  // 8. 跨域策略

三个值得注意的细节：

  • RequestID 排第一，因为后面所有日志都要带上它。这是你排查线上问题时唯一能把一次请求的多行日志串起来的东西。
  • Recoverer 排在日志之后，所以 panic 也会留下访问日志——不是"崩了就没记录"。
  • CORS 在最后一层，并且它的来源白名单同时被 WebSocket 的 Origin 校验复用（realtime.SetAllowedOrigins(origins)），避免两套配置打架。
类比

这一串中间件，等价于你在 Oracle 里用 LOGON 触发器 + 审计策略包住所有数据库访问：每个连接进来先过一遍，决定记录什么、拦截什么、注入什么上下文。

差别是这里的"上下文"用 Go 的 context.Context 往下传，而不是会话级全局变量。

三、三组路由，三种身份

全局中间件之后，router.go 把接口分成几大组，每组有自己的鉴权准入：

路由前缀准入中间件意味着
/health、/readyz、/healthz 无 给人/编排系统探活用，不查数据库权限
/ws 实时层自带的成员校验 人类客户端的实时通道（第 9 课）
/api/daemon/* middleware.DaemonAuth 只认 daemon 令牌，普通用户令牌进不来
登录 / 注册 / 表单类 middleware.RateLimit 等 未认证也要能访问，但限流
其余 /api/* middleware.Auth 必须有会话 Cookie 或 PAT；通过后 context 里塞进当前用户
/api/workspaces/{id}/* 再叠一层 RequireWorkspaceMemberFromURL 或 RequireWorkspaceRoleFromURL 同一组路由内部按权限再分开：读操作 member 即可，写操作要 owner/admin

最后一行是这个文件里最有参考价值的设计模式。同一个 /api/workspaces/{id} 前缀下，作者用两个 r.Group 把它劈成两半：

r.Route("/api/workspaces", func(r chi.Router) {
  r.Route("/{id}", func(r chi.Router) {

    // 成员可见：读列表、读详情、看插件装了啥
    r.Group(func(r chi.Router) {
      r.Use(middleware.RequireWorkspaceMemberFromURL(queries, "id"))
      r.Get("/",              h.GetWorkspace)
      r.Get("/members",       h.ListMembersWithUser)
      r.Get("/plugins",       h.ListPlugins)
      // ...
    })

    // 管理员专属：改工作区、邀请/删人、装插件
    r.Group(func(r chi.Router) {
      r.Use(middleware.RequireWorkspaceRoleFromURL(queries, "id", "owner", "admin"))
      r.Patch("/",            h.UpdateWorkspace)
      r.Post("/members",      h.CreateInvitation)
      // ...
    })
  })
})
关键事实

Multica 的鉴权是"路由级声明"，不是"handler 里 if 判断"。你想知道某个接口谁能调，看路由分组就够了，不用读 handler 实现。

四、handler 之后是什么

中间件放行后进入 handler（server/internal/handler/，130 个文件）。handler 的职责被严格限制在三件事上：

  1. 解析输入：路径参数、查询串、请求体。UUID 怎么解析有硬规定（见下）。
  2. 调 service：真正的业务判断都在 internal/service/。
  3. 写响应：统一的 JSON 形状与错误码。

service 再往下，就是手写 SQL（server/pkg/db/queries/，65 个 .sql 文件）和 sqlc 的生成物（server/pkg/db/generated/）——最终打到 PostgreSQL。

HTTP 请求
  → middleware.Auth                      认证：你是谁
  → RequireWorkspaceMemberFromURL        授权：你能进这个工作区吗
  → handler.ListMembersWithUser          解析参数、调 service、写响应
  → service.xxx                          业务规则
  → queries.ListMembersWithUser  (sqlc)  类型安全的 SQL
  → PostgreSQL
源码原话

In server/internal/handler/, distinguish UUID sources before using them in writes —— handler 里解析 UUID 要分四种来源，用四种不同方法：URL 里可能是"UUID 或人类可读的 slug"（用 loadXxxForUser 解析后取 entity.ID）、纯 UUID 输入（parseUUIDOrBadRequest）、可信内部回环（parseUUID，非法直接 panic）、handler 之外（util.ParseUUID 并检查错误）。（AGENTS.md · Backend UUID Rules）

五、sqlc 是什么（Oracle 视角）

sqlc 做的事：你写 .sql，它读你的建表语句，自动生成强类型的 Go 函数。比如你在 queries/member.sql 里写：

-- name: ListMembersWithUser :many
SELECT ... FROM member m JOIN "user" u ON ... WHERE m.workspace_id = $1;

生成出来的就是 func (q *Queries) ListMembersWithUser(ctx context.Context, workspaceID pgtype.UUID) ([]ListMembersWithUserRow, error)。参数类型错了、字段名写错了，编译期就报错。

类比

Oracle 里你要往 Java/Python 写 SQL，通常是字符串拼接 + 运行时才发现列名写错。Multica 的做法更接近预编译的存储过程 + 强类型接口：SQL 是手写的（不牺牲表达能力），但接口是生成的（不牺牲类型安全）。

对比 server/migrations/：那里管结构变更（DDL，第 10 课），queries/ 只管数据访问（DML）。两者职责不重叠，这是读代码时要分清的第一件事。

六、读这批 Go 代码需要的最小语法

写法含义Python / Oracle 对应
func (h *Handler) GetWorkspace(w http.ResponseWriter, r *http.Request)带接收者的方法，等价于"给 Handler 类加个方法"class Handler: def get_workspace(self, w, r)
func f() (T, error)返回值多一个 error，调用方必须判Python 的 try/except，但由编译器强制检查
ctx context.Context贯穿整个调用链的上下文：超时、取消、请求级元数据会话级 SYS_CONTEXT，但显式传参
`json:"workspace_id"`结构体字段标签，控制序列化出的键名ORM 的列映射注解
interface{ ... }隐式实现：只要方法签名对得上就算实现，不用显式声明Python 的鸭子类型，但由编译器检查

最后一条是读 daemon 与 agent 适配层的关键（第 7、8 课），先记住一句话：Go 的接口是"方法签名契约"，没有 implements 关键字。

七、动手：自己定位一个接口

给你一个具体问题："前端点'成员列表'时打的是哪个接口？" 按下面顺序做，全程不超过 3 分钟：

  1. 打开 server/cmd/server/router.go，搜 members。
  2. 命中 r.Get("/members", h.ListMembersWithUser)，确认它在 RequireWorkspaceMemberFromURL 那个 group 里。
  3. 打开 server/internal/handler/ 搜 func (h *Handler) ListMembersWithUser，看它调了哪个 service / query。
  4. 在 server/pkg/db/queries/member.sql 里找同名 query，看它读了哪张表、过滤了什么。

四步对应四层。以后遇到任何"这个功能怎么实现的"，都用这套路。

八、检索练习

1. 你想快速判断"删除工作区成员"这个接口需要什么权限，最省事的做法是？

2. 要给 Issue 表加一列 pinned_at，你要同时改哪里？

3. 为什么 RequestID 中间件挂在整条链的最前面？

不看上文，写出一个 /api/workspaces/{id}/plugins 这类请求从进来到落库要经过的层次，并说出每层"负责什么、不负责什么"。

  1. 全局中间件链：打 RequestID、记日志、panic 兜底、CORS/CSP。不做鉴权。
  2. 认证中间件 middleware.Auth：确认"你是谁"，把用户塞进 context。
  3. 工作区授权中间件（RequireWorkspaceMemberFromURL / RequireWorkspaceRoleFromURL）：确认"你能进这个工作区吗、你有这个权限吗"。它不关心业务语义。
  4. handler：解析参数（UUID 按来源用不同方法）、调 service、写响应。不写业务规则。
  5. service：业务规则与事务边界。
  6. queries（sqlc 生成物）：执行 SQL。不做权限判断。 → PostgreSQL

一条通用判断法：权限在路由分组，业务在 service，SQL 在 queries。找到哪一层，就找到了该改的文件。
