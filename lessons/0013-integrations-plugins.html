Lesson 13

集成与插件：让 Multica 长出去

Multica 有两套完全不同的"扩展"机制，名字容易混：集成是编译进服务端的第一方适配器，插件是对外公开的第三方契约。这一课把两者分开讲清，重点在插件契约的三个概念。

约 40 分钟 对应源码：internal/integrations/ · pkg/plugincontract/ · packages/plugin-sdk/

一、先分清两套东西

集成 Integrations插件 Plugins
谁写的Multica 自己第三方（也可以是你）
跑在哪编译进 Go 服务端，进程内宿主之外，通过契约通信
代码位置server/internal/integrations/server/pkg/plugincontract/ + packages/plugin-sdk/
你怎么用在界面上连接、授权安装插件、配置它、让它挂载 UI 或订阅事件
命名暗示在 internal/ 里 = 不对外在 pkg/ 里 = 对外公开（第 3 课那条规则）
关键事实

位置本身就是承诺：plugincontract 放在 pkg/ 而不是 internal/，意味着它是可以被外部依赖的稳定契约。源码注释也把这条写明了：

Package plugincontract defines the versioned public contract between plugin authors and the Multica host. It must stay independent from private handlers, services, and database implementations.

二、集成：三类，看目录就懂

server/internal/integrations/ 下的子目录就是全集：

channel, composio, dingtalk, ghsnapshot, lark, slack, telegram, vcs, wecom
类别目录它让你做什么
代码仓库 vcs、ghsnapshot 把 Issue 和 PR 关联起来；仓库侧事件回灌成 Multica 里的动作
即时通讯 slack、lark、dingtalk、telegram、wecom、channel 在聊天里建 Issue、指派 Agent、收进度通知
第三方 SaaS 桥 composio 把外部工具接入成 Agent 可用的能力

它们在路由上的入口全是 webhook 形态——都是"外部系统打进来"：

POST /api/webhooks/github                    # GitHub 事件
GET  /api/github/setup                       # GitHub 安装回调
POST /api/webhooks/vcs/{connectionId}        # 各 VCS（Forgejo/Gitea/GitLab 等）
POST /api/webhooks/autopilots/{token}        # Autopilot 的 webhook 触发器
GET  /api/integrations/composio/callback     # Composio 授权回调

注意最后一条与 Autopilot 的联动：Autopilot 的 webhook 触发器就是靠一个带 token 的 URL 收事件的——这也是第 5 课那个 deferred 状态的另一个来源（定时或 webhook 一到就排一条 Run）。

三、插件契约：三种关系

这是本课的核心。plugincontract/manifest.go 开头的注释把整个模型压缩成了三行，原文照抄：

源码原话 
A plugin relates to Multica in exactly three ways:
  - Action   (plugin -> Multica): host capabilities the plugin calls.
  - Hook     (Multica -> plugin): plugin capabilities the host calls.
  - Resource (no call at all):    static contributions such as skill text.
关系方向例子
Action插件 → Multica插件调用宿主的读写能力（受 scope 限制）
HookMultica → 插件宿主在事件发生时回调插件
Resource无调用静态贡献，例如一段 Skill 文本

紧接着还有一句看起来抽象、但很值钱的说明：

源码原话

"Who triggers" and "what capability is called" are orthogonal: a hook is declared once and may be invoked by any of the triggers it opts into.

翻译/展开：hook 声明一次，而"谁能触发它"是另一个维度。触发器（event 事件、schedule 定时）只是 opt-in 声明，不改变 hook 本身做什么。

这带来一个很干净的心智模型：能力与触发解耦。你想让同一个能力既能被"事件"触发又能被"定时"触发，不需要写两份实现。

类比

这在 Oracle 里的对应物是包 + 作业的分离：PKG_X.DO_WORK 是能力（被调用的东西），而"谁来调"可以是应用代码、也可以是 DBMS_SCHEDULER 的 job、也可以是一个触发器。

把"能力"和"触发方式"写在一个地方的代码，通常会在需要第二种触发方式时被迫复制一遍。Multica 的设计从契约层面避免了这件事。

Surface：宿主挂载的 iframe

注释里对 surface 的定义很短：surface 是宿主挂在固定位置的 iframe。也就是说插件不只是后台逻辑，它可以有界面，但界面是被挂载到宿主里的，而不是插件自己独立成站。

这一点在路由上有痕迹：插件界面走 GET /plugin-surfaces/{token} 提供，而给用户的是短期启动地址 /api/workspaces/{id}/plugins/{installationId}/surfaces/{surfaceKey}/launch。源码注释解释了为什么这么做：

源码原话

Member-visible because opening an issue is what asks for it; executable bytes stay off the authenticated app/API origin.

即：可执行的插件字节不放在已认证的主站源上，而是通过一个短期 token 换到独立路径去加载。这是把"插件"和"应用本体"的信任域分开——和浏览器同源策略打交道的常规做法。

Scopes：一份封闭清单

插件能调用宿主哪些能力，由 manifest 里声明的 scope 决定。清单是封闭的（源码原话：This list is complete and closed; anything else is rejected at parse time）：

Scope含义
issues:read / issues:write读写 Issue
comments:read / comments:write读写评论
tasks:read / tasks:write读写 Run
agents:read读 Agent（注意：没有 agents:write）
members:read读成员
storage:user / storage:workspace两种粒度的存储
net:<domain>唯一带参数的 scope：控制插件能访问哪些外部域名

net: 这个 scope 的作用点很关键：它同时决定两件事——iframe 的 CSP connect-src 白名单，以及 hook 传输时的宿主校验。

关键事实

只声明一次、两处生效。这是"用一个配置源代替两个平行配置"的典型手法——本项目多处都用这个思路（还记得第 4 课 CORS 白名单被 WebSocket 的 Origin 校验复用吗？同一招）。

Hook 触发器与配置表单

两个细节值得记：

  • event 与 schedule 都是异步的，两者都不阻塞面向用户的宿主请求。也就是说插件的回调变慢不会拖慢你的界面。
  • schedule 是轮询原语，不是高频定时器，有一个下限。源码给的理由很实在：The floor keeps one installation from turning its manifest into an unbounded source of outbound traffic——防止一个插件靠写 manifest 把自己的出站流量变成无限。
  • 配置表单由宿主渲染：契约里只支持 JSON Schema 的一个故意很小的子集，因此插件不需要自带表单 UI。

四、两边的代码在哪

位置语言角色
server/pkg/plugincontract/manifest.goGo契约定义：manifest 结构、scope、hook 触发器、surface 类型、resource 类型
server/pkg/plugincontract/capabilities.goGo宿主提供的能力清单
server/pkg/plugincontract/bundle.goGo打包与校验（含体积上限 MaxManifestSize）
packages/plugin-sdk/TypeScript给插件作者的 SDK：index.ts + protocol.ts
server/internal/service/plugin*.goGo服务端实现：安装、钩子调用、事件分发、调度、存储、token、包管理（十几文件，全部在 internal/）

注意最后一行：service/ 下一整族 plugin_*.go 文件覆盖了 plugin.go、plugin_action.go、plugin_hook.go、plugin_event_bridge.go、plugin_event_dispatch.go、plugin_mcp_transport.go、plugin_schedule.go、plugin_skill.go、plugin_storage.go、plugin_token.go、plugin_package.go、plugin_agent_tools.go。

这个文件清单本身就是插件能力的地图——想知道插件系统"能做哪些事"，读文件名就够了。

五、权限：谁能装插件

回到第 4 课那张路由分组表，插件相关接口的准入分得很清楚：

动作角色要求
看装了哪些插件member 即可
获取插件界面的启动地址member 即可
安装 / 配置 / 移除插件owner 或 admin

源码注释给的理由是：member 可见是为了让他知道自己所在的工作区挂了什么、持有哪些 scope；而改动必须由管理员做。

小心

"member 能看到插件持有哪些 scope"这件事是安全上的必要设计：插件是在你的工作区里以该工作区的身份行动的。一个要了 issues:write 的插件能改你的任务单——所以普通成员有权知道它存在、它要了什么。

六、检索练习

1. 插件契约里 Hook 与 Action 的区别是？

2. 你想让同一个插件能力既能被"新评论"触发、也能每天定时触发，正确做法是？

3. 插件需要调用一个外部 API，安全上由谁控制、控制在哪两处生效？

不看上文，说出插件与 Multica 的三种关系，各举一例；并说明为什么这些契约放在 pkg/ 而不是 internal/。

  • Action（插件 → Multica）：插件调用宿主能力，例如读 Issue、写评论。受 scope 限制。
  • Hook（Multica → 插件）：宿主在事件或定时点回调插件。声明一次，可被多种触发器调用。
  • Resource（无调用）：静态贡献，例如一段 Skill 文本。

放在 pkg/ 的原因：Go 的 internal/ 是编译器强制的外部不可 import 边界（第 3 课）。契约需要被插件作者依赖，所以必须放在 pkg/；而它的实现（安装、调度、存储、token）全部留在 internal/service/plugin_*.go，不对外暴露。

这就是"公开契约 + 私有实现"的标准切法：定义对外，实现封起来。
