一、名字里藏着定位

Multica = Multiplexed Information and Computing Agent。名字取自 1960 年代的 Multics 操作系统——那个第一次把"分时"概念带进计算机的系统，让多个人共用一台机器，各自感觉像独占一台。

为什么拿这个当名字？因为 Multica 想解决的是同一类问题，只是"共用的用户"变了：

类比

你现在的开发状态大概是：3 个终端标签页分别跑着 Claude Code、Codex、还有一个别的 Agent。每个窗口都记不住上一次聊了什么，你每天要第四次解释同一段背景。加得越多，你花在"盯梢"和"复述"上的时间越多。

Multica 的说法是：把这些 Agent 和你自己放进同一个工作台，用派活给同事的方式派活给 Agent。它自称是开源的 Managed Agents 平台。

二、它不做什么，比它做什么更重要

这句话是理解整个架构的钥匙：

关键事实

Multica 不提供模型，也不直接执行代码。它驱动你机器上已经装好并登录的编码 Agent CLI（README 里列了 26 种：claude、codex、cursor-agent、copilot、opencode、kimi、grok、qwen…… 完整清单在 scripts/agent-cli-command-names.txt）。

换 provider 是下拉框的事，不是一次迁移。

把它拆成三层看就清楚了：

层次归谁管产物
协作数据（谁派了什么活、进度如何、花了多少钱）Multica 的 Go 服务端 + PostgreSQLIssue、Run 记录、执行日志、用量
执行调度（什么时候唤醒哪台机器、给什么凭据）Multica 的服务端 + 你机器上的 daemon一条条 queued → running 的任务
真正干活你已有的 Agent CLI代码改动、命令执行、PR

所以你在架构图里会看到一条很别扭的线：客户端 → Go 服务端 → daemon → Agent CLI。服务端从不下场执行，它只负责"派活、记账、发凭据"。

给你的背景

你有 Oracle + Python 背景，这对读这个项目是优势而不是劣势：

  • PostgreSQL 那套迁移、索引、事务在这儿是主线，不是配菜（第 6 课专门讲）。
  • Go 代码里大量的 service / repository 分层，本质是你在 PL/SQL 里见过的"业务逻辑与数据访问分离"。
  • 唯一的门槛是 Go 语法与 TypeScript 类型系统。这两样本课只讲"读懂所需的最小集"，不会变成语言教程。

四、授权模式：一个必须知道的"坑"

Multica 的许可证叫 Multica License——完整的 Apache 2.0 文本加上额外条件，覆盖三个方面：托管服务、商业嵌入、品牌。原文在 LICENSE，署名要求在 NOTICE。

实践含义：

  • 自部署、修改、在内网给团队用 —— 可以。
  • 把它做成对外提供的托管服务，或者嵌进你要卖的产品 —— 需要先读条款。

顺带说一句它的怪异之处：.gitignore 里写着 server/bin/、server/daemon、server/multica，而仓库里确实有 server/cmd/multica/。这不是打错字，是同一个 Go 二进制既当 CLI 又当 daemon 的证据——第 8 课会展开。

五、检索练习（靠回忆作答）

1. 关于 Multica 与"模型"的关系，下面哪句最准确？

2. 你的源码在哪一刻离开过自己的机器？

3. "Multica" 这个名字致敬的是？

不看上面的表格，写出你机器上会出现的三个进程/组件，以及各自负责什么。

  1. 浏览器 / 桌面端（或 CLI）：你的操作入口，通过 HTTP + WebSocket 跟服务端说话。
  2. Go 服务端：保存工作区、Issue、Run 记录与用量；决定哪台机器该干活；签发运行级凭据。它不执行你的代码。
  3. Agent daemon：跑在你机器上的 Go 进程，领取 Run、准备本地目录、spawn 你已登录的 Agent CLI，并把流式事件回传给服务端。

严格说还有第四个：被 spawn 的 Agent CLI 进程本身（claude、codex……），它才是真正读你代码、改你文件的那个。
