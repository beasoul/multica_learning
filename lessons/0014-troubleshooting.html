Lesson 14

收官：分诊故障，然后动手改一处

最后一课做两件事：把前面 13 课的零件组装成一套排查流程（而不是一堆要背的故障列表），再给你一条最小改动的路径——改得动，才算真读懂。

约 40 分钟 对应源码：troubleshooting.zh.mdx · tasks.zh.mdx · AGENTS.md（Change and Delivery Rules）

一、固定开场：三条命令

不管是"连不上"还是"不干活"，先打这三条，把事实钉住：

multica auth status                    # 我是谁、令牌还有效吗
multica daemon status --output json    # 检测到哪些 Agent、监听哪些工作区
multica daemon logs --lines 100        # 最近的现场
关键事实

daemon logs 在输出日志内容之前会先打印它解析到的绝对路径。这一行的价值在于：它能立刻告诉你"你看的是不是那个正在写的文件"（第 8 课那个坑）。看不出问题时先看这一行。

二、按"Run 停在哪"分诊

这是本课的核心方法。第 5 课那张状态机表现在变成分诊表——先确定卡在哪个状态，再走对应的分支，比背一份故障清单有效得多。

分支 A：一直 queued（没有运行时来领）

依次检查四件事：

  1. Agent 绑定的运行时是否在线；
  2. 运行时是否检测到了该 Agent 配置的那个工具；
  3. Agent 是否还有可用并发额度（默认单个 Agent 最多同时 6 次运行）；
  4. daemon 是否还有全局执行容量（默认单 daemon 最多同时 20 次）。
multica daemon status --output json
multica agent get <agent-id>
multica issue runs <issue-id>
重要澄清

"排队很久"本身不是故障。官方文档明确说明：运行时离线时，运行会继续排队；只有该运行时的心跳缺席超过重连宽限期、并且这条运行自己也已经等满这么久，才会失败。

所以排在忙碌运行时后面的长队列不会因为"等太久"被判失败。看到 queued 先查上面四项，不要急着下"系统坏了"的结论。

如果运行时列表里缺少预期工具：先在同一个系统账号和 PATH 下确认那个工具能跑、已登录，再 multica daemon restart。

分支 B：停在 waiting_local_directory（目录被占）

含义：另一条在途运行正在使用同一个本地目录。互斥存在的意义是避免两个 Agent 同时改同一份文件。

关键补充（这一点文档里写得很有用）：

  • 这种等待只存在于目录的 in_place（原地）模式。如果这个目录是 git 仓库，把资源切到 worktree（并行）模式就没有队列了——每次运行拿到自己的 worktree，以分支形式交回结果，谁都不用等谁。
  • 这个目录互斥是daemon 在内存里维护的，不写磁盘锁文件。所以怀疑锁状态异常时，multica daemon restart 即可释放——没有需要你手动删除的文件。
关键事实

这一条是最好的"架构知识转化为操作"的例子：因为它不落盘，所以不存在"删锁文件"这种操作。不了解实现的人会去找一个根本不存在的文件。

分支 C：running 但没产出 / 工具起不来

daemon 在线不等于工具可用。打开这次运行的详细记录，按这个清单查：

检查项为什么
工具是否已登录daemon 只负责 spawn，登录态是工具自己的事
API key / 额度 / 模型权限是否可用任务能起但请求会被拒
Agent 选的模型与思考级别是否被该工具支持第 8 课那些 MULTICA_*_MODEL 覆盖项设错就会这样
本地工作目录是否存在且可写目录被删、权限变了
自定义参数或环境变量是否有效参数解析失败会让进程立刻退出

最快的验证方法：在执行那台机器的终端里，直接手工运行同一个工具。工具自己都起不来，就先修它的配置，再从执行日志重试。

三、分支 D：daemon 连不上服务端

常见原因就五条：

  1. CLI 尚未登录，或本机令牌已失效；
  2. daemon 连了错误的服务端（profile 配错）；
  3. 执行那台机器访问不到 API —— DNS、TLS、防火墙拦截；
  4. 当前账号已经不在目标工作区里了；
  5. 本机没装任何受支持的 AI 编程工具，daemon 因此起不来。
multica login
multica daemon restart
multica config show        # 确认 server_url / app_url 对不对
小心

自部署场景有一条极容易被忽略的指引：要从"执行电脑"去请求 API 的 /health——在服务器本机测是测不出执行机侧的 DNS、TLS、防火墙问题的。

这是一条通用的排查纪律：在出问题的那一侧测，不要在你的机器上测。

四、分支 E：界面不实时了

按顺序查（对应第 9 课）：

  1. FRONTEND_ORIGIN 是否与浏览器实际打开的地址一致；
  2. HTTPS 页面是否通过 wss:// 连接；
  3. 反向代理是否转发了 WebSocket 的 Upgrade 请求（这是最常见的部署踩坑点）；
  4. 浏览器登录是否已过期。

顺便复习第 9 课的结论：实时失效不会让数据变错，只会让它看起来旧。刷新页面能拿到正确状态，说明问题就在实时链路。

六、动手改一处：三个梯度的选择

MISSION 的最后一条是"能在源码里自己定位并改"。给你三个梯度，按你当时的状态挑一个：

梯度改动要动的文件验证
S · 前端展示 在某个页面加一段只读信息（例如 Run 列表里多显示一个字段） packages/views/...，必要时 packages/ui pnpm typecheck + pnpm test
M · 前端数据 给 Issue 列表加一个新筛选条件（沿用现有 query hooks） packages/core（查询参数）+ packages/views（筛选控件） make check 或按范围跑
L · 全栈只读 新增一个只读 HTTP 接口并接进前端 router.go + internal/handler + pkg/db/queries/*.sql（make sqlc）+ packages/core/api make check

我建议从 M 开始。理由：它同时踩到第 3 课（分层边界）和第 4 课（数据在哪），又不用碰数据库迁移——覆盖了最多知识点，风险最低。

改代码前必须知道的五条规矩

全部来自 AGENTS.md 的 Change and Delivery Rules：

  1. 保持改动范围小，复用现有模式；代码注释用英文。
  2. 不要自作主张加兼容层——不加内部 shim、双写、回退路径或旧版适配器（除非被要求）。注意这不放松 API 响应兼容性的要求。
  3. 新增全局 pre-workspace 路由命名有规则（单词或 /{名词}/{动词}，不用连字符根名）；改保留 slug 要更新 server/internal/handler/reserved_slugs.json、跑 pnpm generate:reserved-slugs，并提交生成的 packages/core/paths/reserved-slugs.ts。
  4. 用原子的 convention commits，并套用仓库的 PR 模板。
  5. 改了 SQL 要 make sqlc；改了查询/接口要同步更新对应的 zod schema 与「畸形响应」测试。

七、检索练习（收官题）

1. 一条 Run 已经 queued 两个小时，运行时才离线半小时。它应该？

2. 你怀疑 waiting_local_directory 的锁状态异常，正确做法是？

3. 自部署环境下执行机连不上服务端。为什么"在服务器上 curl 自己的 /health"帮助不大？

不看上文，写出你的完整排查流程（从现象到结论）。

  1. 固定开场：multica auth status → daemon status --output json → daemon logs（先看它打印的绝对路径）。
  2. 定位 Run 的状态，据此分诊：
    • queued → 查运行时在线 / 工具检测 / Agent 并发额度 / daemon 全局容量。
    • waiting_local_directory → 目录互斥；考虑切 worktree 模式；要释放就重启 daemon。
    • running 无产出 → 查工具自身（登录、key、模型与思考级别、目录可写、自定义参数），并手工直接运行该工具验证。
    • failed → 读运行详情里的失败原因（这是唯一"自带答案"的状态）。
  3. 若是连接类问题：查五条常见原因，并在执行机上请求 API 的 /health，用 config show 核对 server_url。
  4. 若是实时类问题：查 FRONTEND_ORIGIN、wss://、反代是否转发 Upgrade、登录是否过期。
  5. 还定位不了：multica daemon start --foreground 看启动过程；然后去 GitHub Issues 搜同类问题。

核心心法：先确定"卡在哪个环节"，再走那一个分支。不要从故障清单第一条开始逐条试。
