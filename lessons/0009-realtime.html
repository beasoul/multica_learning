Lesson 09

实时同步：两条 WebSocket 通道

为什么你在界面上能眼看着 Agent 一步步干活？因为有一整套事件系统。这一课讲清两条通道的分工、事件的命名与粒度，以及前端收到事件之后到底改了什么。

约 35 分钟 对应图表：06 实时事件数据流 对应源码：pkg/protocol/events.go · internal/realtime/ · internal/daemonws/ · packages/core/realtime/

一、两条通道，两种用户

Multica 的实时层是两套独立系统，不要混着理解：

通道 A：/ws通道 B：/api/daemon/ws
连接者人用的客户端（Web / 桌面端）daemon（机器）
代码位置server/internal/realtime/server/internal/daemonws/
鉴权会话 Cookie 或 PAT + 成员校验middleware.DaemonAuth（只认 daemon 令牌）
语义广播：把变更推给关心它的人双向 RPC：服务端还会反过来请求 daemon 做事
典型消息issue:updated、task:running、inbox:new"这个 Runtime 有可领的任务了"、模型列表查询、插件钩子调用
关键事实

通道 A 的成员校验由三样东西完成：membershipChecker（你是不是这个工作区的人）、patResolver（PAT 解析）、slugResolver（把工作区 slug 换成 UUID）。这三者都定义在 router.go 里、创建时传给 realtime.HandleWebSocket。

也就是说：WebSocket 不是"连上就完事"的免检通道，它自带一套自己的准入。

二、事件的命名空间

所有事件常量集中在 server/pkg/protocol/events.go，按领域分组、冒号分隔：

前缀代表事件
issue:issue:created / issue:updated / issue:deleted
comment:comment:created / comment:resolved / reaction:added
agent:agent:status / agent:created / agent:archived
task:task:queued / task:dispatch / task:running / task:progress / task:completed / task:failed / task:cancelled
inbox:inbox:new / inbox:read / inbox:archived
workspace: member: subscriber: skill: chat:各自领域的增删改
类比

冒号前缀就是点名空间下的层级键，等价于 Oracle 里用包名给过程分域：PKG_ISSUE.CREATE、PKG_TASK.COMPLETE。客户端可以只订阅 task: 这一族，不用逐个枚举。

三、事件粒度：一句注释就讲透了

这里有个很容易被忽略但很值钱的设计判断。源码注释原文：

源码原话

Each event maps to a status transition on agent_task_queue. Front-end subscribes by `task:` prefix and invalidates the workspace task snapshot, so the granularity here is "what does the user want to see change" — not "every internal status flip".

翻译：事件的粒度是按"用户想看到什么变化"设计的，不是按"内部状态变了多少次"设计的。

这解释了为什么没有 task:heartbeat、task:lease-extended 这类事件——那些内部翻转对用户没有意义，推出去只会制造噪音。你在界面上能看到的状态变化，恰好就是 task:* 事件的全集。

四、前端收到事件之后做什么

这一点必须和第 3 课的 State Rules 联起来看。AGENTS.md 的规定是：

源码原话

WebSocket events patch or invalidate Query caches, not server payloads in Zustand.

也就是说，实时事件只动 TanStack Query 的缓存，绝不去改 Zustand 里的服务端数据副本。两种处理方式：

方式什么时候用代码里的样子
invalidate（作废重查） 结果不确定、或让服务端自己算最稳 qc.invalidateQueries({ queryKey: issueKeys.all(wsId) })
patch（就地打补丁） 结果可预测，能直接算出新状态 qc.setQueryData(chatKeys.messages(sessionId), ...) 追加一条消息

看 packages/core/realtime/use-realtime-sync.ts 的实际写法：Issue 类事件走 invalidateQueries（issueKeys.all(wsId)）；而聊天消息这类"追加一条、顺序明确"的走 setQueryData 直接补进去。

小心

注释里还有一句更严的话：聊天的 task:* 事件是 invalidate，而不是乐观的 setQueryData。原因是这类事件的到达顺序不保证，乐观写入可能把状态改错。

规则可以记成一句话：能确定的补丁就补丁，不确定的一律作废重查。

五、服务端多实例了怎么办

一台服务端上，realtime/hub.go 管着所有连接与订阅。但服务端可能不止一个实例——A 实例上的客户端，需要收到 B 实例上发生的变更。仓库里对应的答案是这几个文件：

  • realtime/broadcaster.go：广播抽象
  • realtime/redis_relay.go：用 Redis 做跨实例转发
  • realtime/sharded_stream_relay.go：分片流转发
  • realtime/stream_retention.go：保留策略（重连后能补上错过的片段）

你不需要现在读完它们。要记住的是这个判断：实时层的水平扩展是"转发"问题，而不是"让每个实例都查全量数据库"的问题。

六、为什么敢说"实时只是加速器"

把这一课和第 6 课连起来，整个系统的可靠性论证就完整了：

  1. 权威状态在 PostgreSQL 里（服务端是唯一写方）。
  2. 实时通道把变更尽快告诉客户端。
  3. 客户端丢事件、断开重连、甚至根本没连上——重新查询就能拿到正确状态。

所以哪怕实时层整个挂掉，Multica 也不会"算错"，只会"看起来慢一点"。这是个很干净的设计边界。

七、检索练习

1. /ws 与 /api/daemon/ws 的根本区别是？

2. 为什么实时事件里没有"心跳延长了租约"这种消息？

3. 收到 issue:updated 后，前端正确做法是？

不看上文，说出"实时事件 → 界面更新"这条链上的五个环节。

  1. 某处发生变更（例如 daemon 调 POST .../complete）。
  2. 服务端写入 PostgreSQL，并在事件源构造一条带冒号命名空间的事件（task:completed）。
  3. realtime/hub.go 按订阅范围把事件推给关心它的连接（多实例时经 relay 转发）。
  4. 客户端 use-realtime-sync 收到事件，按"确定就 patch、不确定就 invalidate"处理 Query 缓存。
  5. React 组件因缓存变化重渲染，你看到进度条走完了。

补充：这条链上的任何一环断掉，客户端重新查询都能恢复正确状态——这是"数据库是事实源"的直接推论。
