Lesson 02

领域模型：先把八个名词钉死

Multica 的界面、HTTP API、数据库表、实时事件名全都用同一套词汇。这些名词不认识，后面每一课你都会卡在"这个词到底指什么"上。这一课只做定义，不做实现。

约 30 分钟 对应图表：01 系统架构总览 对应源码：apps/docs/content/docs/concepts.zh.mdx · AGENTS.md

一、为什么必须先学名词

你去看一条真实日志：

task:dispatch  issue=ENG-412  assignee_type=squad  runtime=r-9f2c  workspace=ws-1a

这一行里有 6 个领域名词。如果 assignee_type 和 runtime 的区别说不清，你就没法判断"这条日志说明它开始干活了没有"。

关键事实

Multica 的领域模型是三层分离的：意图（Issue：我想让人做什么）／执行（Run：某次真的去做）／能力（Agent + Runtime：谁、在哪台机器上能做）。

把这三层混在一起，是整个系统最容易产生的误解。

二、八个名词，一张表

名词一句话定义在哪能看到它
Workspace 工作区 租户与权限边界。所有数据都挂在某个 workspace 下，所有查询都按 workspace_id 过滤。 请求头 X-Workspace-ID；界面左上角切换器
Issue 任务单 人的工作单元。有标题、描述、状态、标签、评论，可以被"指派"。 看板卡片；issues 相关表
Run 执行 一次"让某个 Agent 去做这个 Issue"的尝试。代码里它叫 task，界面上叫 Run。 agent_task_queue 表；Run 详情页；task:* 事件
Agent 智能体 一份配置：用哪个 provider（哪种 CLI）、什么系统提示、挂哪些 Skill。它不是进程。 智能体设置页；agentconfig 包
Runtime 运行时 某台机器上、某个 provider 的一次实际可用安装，由 daemon 扫描本机后注册上来。 runtimes；daemon status 输出
Squad 小队 一组 Agent 的集合，可以整体当作被指派人，也可以定义内部谁先谁后。 squads；squad.sql
Skill 技能 可复用的提示词／流程包，可以派给 Agent 或 Squad，运行时注入到 CLI。 skills；internal/skill、pkg/skillbundle
Autopilot 自动驾驶 自动化触发器：定时（cron）或 webhook 一到就创建 Issue 并派活。 autopilots.zh.mdx；internal/scheduler

还有两个你马上会遇到的：

  • Project 项目：一个代码仓库的绑定关系（Git/VCS 连接、默认分支、本地目录规则）。它决定 daemon 把哪个目录交给 Agent。
  • Inbox 收件箱：需要你处理的流。Agent 干完交回评审、有人 @ 你、Run 失败——都进 Inbox。

三、三个最容易搞错的地方

1. Issue 和 Run 是 1:N，不是 1:1

一个 Issue 可以有很多个 Run：第一次失败了重试一次、换一个 Agent 再来一次、你加了条评论触发了"补充执行"。

类比

在 Oracle 里，Issue 像一张业务单据，Run 像这张单据对应的执行记录——用 DBMS_SCHEDULER 跑一次就是一个 job run 实例，用 PL/SQL 手工重跑一次又是一个。单据只有一张，执行记录可以有很多条，每条都有自己的状态和时间戳。

这也解释了为什么 Run 详情页要显示"这是第 3 次执行"。

2. Agent ≠ Runtime（最关键的一条）

这是新用户最常混的一对：

AgentRuntime
是什么逻辑身份 + 配置物理能力（某台机上装好的某个 CLI）
谁创建你，在界面上手动建daemon 扫本机后自动注册
数量一个 Agent 对应零到多个 Runtime一台机 + 一个 provider = 一个 Runtime
会消失吗不会，除非你归档它会。daemon 停了、CLI 卸载了、版本被降级了都会掉线

所以会出现这种情况：界面里那个叫"前端重构手"的 Agent 好好的，但派活给它总是失败——真正的原因是你笔记本上的 daemon 没起来，它对应的 Runtime 全部离线。

3. 被指派人（assignee）是多态的

一条 Issue 可以被指派给人、Agent 或者Squad。AGENTS.md 里对这条有硬规定：

源码原话

Assignees are polymorphic: interpret assignee_id together with assignee_type.（AGENTS.md · Backend UUID Rules）

实践含义：数据库里只有一列 assignee_id，光看它对不出是人还是 Agent。必须配上 assignee_type 一起读。这一条在你自己写 SQL 查数据时会直接决定结果对不对。

把关系写成一棵归属树（左边的拥有右边的）：

Workspace
├─ Member（人）
├─ Agent（配置）──────── 可挂 Skill / 可组进 Squad
├─ Squad（Agent 的集合）
├─ Project（仓库绑定）
├─ Autopilot（定时/webhook 触发器）
└─ Issue（工作单元）
   └─ Run（= task，执行尝试）×N
      └─ 指向：Runtime（在哪台机、哪个 CLI 上跑）
      └─ 指向：Agent / Squad（谁在跑）
      └─ 产生：执行日志、消息、用量、Inbox 通知

五、检索练习

1. 你在界面上看到 Agent「前端重构手」状态正常，但派活总是失败。最可能的原因是？

2. 同一个 Issue 下出现 5 条 Run 记录，最合理的解释是？

3. 你写 SQL 想统计"被指派给 Agent 的 Issue 数量"，为什么不能只按 assignee_id 分组？

不看上面的树，凭记忆写出：一个 Issue 从被创建到一次执行结束，会牵出哪些对象？它们之间谁指向谁？

  1. Issue 在某个 Workspace 下被创建，带上 assignee_type + assignee_id（指向 Member / Agent / Squad）。
  2. 指派动作触发一条 Run（表名 agent_task_queue），它引用 Issue、被指派的 Agent/Squad，以及一个 Runtime。
  3. Runtime 属于某台机器上的 daemon；daemon 拿到 Run 后，按 Project 的仓库/目录规则准备本地路径，spawn 对应的 Agent CLI 进程。
  4. CLI 执行期间，daemon 把进度和消息回传服务端；服务端写成 Run 的日志/用量，并给相关的人推 Inbox 通知。
  5. 结束时 Run 变成 completed / failed / cancelled（状态机是第 5 课的内容）。
