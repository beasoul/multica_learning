Lesson 05

Run 的状态机：八个状态，一条主线

你在界面上看到的每一个进度指示、每一条"任务卡住了"的抱怨，本质都是在问同一个问题：这条 Run 现在处于哪个状态？这一课把状态机钉死——它是后面 daemon、时序、排查三课的共同地基。

约 35 分钟 对应图表：03 Run 生命周期 对应源码：server/pkg/protocol/events.go · pkg/db/queries/agent.sql · internal/service/task.go

一、状态定义就在事件的注释里

Multica 有一份效率极高的"源码即文档"：server/pkg/protocol/events.go。每条 Run 事件后面的注释，直接写明了它对应的状态转移。原文照抄：

EventTaskQueued                = "task:queued"                  // ∅ → queued (enqueue / retry create)
EventTaskDispatch              = "task:dispatch"                // queued → dispatched (daemon claim)
EventTaskRunning               = "task:running"                 // dispatched → running (daemon started)
EventTaskWaitingLocalDirectory = "task:waiting_local_directory" // dispatched → waiting_local_directory
EventTaskProgress              = "task:progress"
EventTaskCompleted             = "task:completed"               // running → completed
EventTaskFailed                = "task:failed"                  // running → failed
EventTaskCancelled             = "task:cancelled"               // * → cancelled
关键事实

每一个状态转移都对应一条实时事件。前端不需要轮询，它订阅的是"状态变了"这件事本身。这也意味着：如果你在界面上看到状态没变，服务端八成也没变——问题在上游，不在展示层。

二、八个状态各是什么

状态含义谁把它推到下一个状态
（不存在）指派动作发生但还没入库服务端创建记录 → deferred 或 queued
deferred已建但未到点：带了 fire_at 的定时唤醒任务，时间没到之前完全不动调度器到点后 → queued
queued在队列里等一个能干的 Runtime 来认领daemon 认领 → dispatched
dispatched已被某台机器的 daemon 认领，凭据已签发daemon 启动 CLI → running；或目录被占 → waiting_local_directory
waiting_local_directory挂起等目录：要用的本地目录正被另一条 Run 占着目录释放后 → running
runningAgent CLI 进程已经在跑CLI 结束 → completed / failed
completed终态：正常结束，交回评审—
failed终态：出错结束，带错误信息—
cancelled终态：被人或系统取消（任何状态都能到这里）—

创建时怎么决定是 deferred 还是 queued？源码里的写法非常直白：

CASE WHEN fire_at IS NOT NULL THEN 'deferred' ELSE 'queued' END

（server/pkg/db/queries/agent.sql）——有定时点就排期，没有就直接入队。一句话解释了两个状态的差别。

类比

DBMS_SCHEDULER 的 job 也有 SCHEDULED / RUNNING / COMPLETED / FAILED，并且一次 job run 是一个独立实例，有自己的状态与日志。Multica 的 Run 基本就是这个模型。

deferred 对应你给 job 设了一个未来的 start_date——已建成、已登记，但还没到该跑的时候。

四、为什么多出这两个"怪"状态

一个普通的任务队列只需要 queued / running / done。Multica 多出 waiting_local_directory 和 deferred，恰好暴露了它和普通队列的本质差别：

1. waiting_local_directory：因为"机器"是一等公民

Agent 不是跑在无状态的容器里，而是跑在你机器上的某个真实目录。同一个目录不能同时被两个 Agent 改。源码对它的描述只有一句：

源码原话

dispatched → waiting_local_directory (daemon parked on a busy local_directory path)——daemon 因为目标本地目录被占用而"停车"等待。

于是 daemon 报的状态不是"失败"，而是"我在等"。这是一个只有把"本地环境"纳入调度才会出现的状态。

2. deferred：因为触发方式不止"立刻"

Issue 可以被定时唤醒（wakeup）、被 webhook 触发、被 Autopilot 排期。这些情况下 Run 会先建成一条带 fire_at 的 deferred 记录——先占位，到点才排进队列。这样做的好处是：你提前就能在界面上看到"它会在明天 9 点跑"。

五、谁有权改状态

这一点非常重要，它解释了整个系统的信任模型：只有服务端写数据库。daemon 是通过一组固定 HTTP 接口"请求"服务端改状态，而不是自己连库。

daemon 调用服务端动作
POST /api/daemon/tasks/claimqueued → dispatched，并签发运行令牌
POST /api/daemon/tasks/{taskId}/startdispatched → running
POST /api/daemon/tasks/{taskId}/wait-local-directorydispatched → waiting_local_directory
POST /api/daemon/tasks/{taskId}/progress记进度（不改状态）
POST /api/daemon/tasks/{taskId}/completerunning → completed
POST /api/daemon/tasks/{taskId}/failrunning → failed
GET /api/daemon/tasks/{taskId}/status只读：daemon 用它确认"我这条还在吗"

全部在 router.go 的 r.Route("/api/daemon", ...) 分组里，统一挂 middleware.DaemonAuth——普通用户令牌根本进不了这个分组。

六、把状态机用起来：三个典型故障

现象停在哪个状态最可能的原因（第 14 课会展开）
点了指派，一直不动queued没有可用的 Runtime 来认领：daemon 没起、或 Agent 的 provider 在本机没装
"开始"很久了但没产出dispatcheddaemon 认领后崩了 / 网络断了，没走到 start
进度条一直转圈waiting_local_directory同一个本地目录被另一条 Run 占着；等它结束就会自动继续
小心

别把"卡住"和"失败"混在一起。这三个现象里没有一个是 failed。真正失败会自动带着错误信息进终态。停在非终态，说明流程还没走完，只是卡在某一环——这两类问题的排查路径完全不同。

不看上面的图，凭记忆写出从"指派"到"终态"的主线状态顺序，并指出哪两个状态是分叉。

主线：

queued → dispatched → running → completed / failed
（cancelled 可从任意状态进入）

两个分叉：

  • 入口分叉：创建时若有 fire_at 则是 deferred，到点才转 queued；否则直接 queued。
  • 出口分叉：dispatched 之后，如果目标本地目录被占用，先转 waiting_local_directory，目录释放后再转 running。
