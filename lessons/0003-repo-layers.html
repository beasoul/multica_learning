Lesson 03

仓库分层：为什么文件不能随便放

Multica 是一个"一套代码跑三个端"的 monorepo。它的分层不是风格偏好，而是有硬边界的工程契约——哪一层能 import 哪一层，写死了。搞懂这个，你才能知道"我想改的功能该动哪个文件"。

约 35 分钟 对应图表：02 仓库分层与依赖方向 对应源码：AGENTS.md · packages/ · apps/ · server/internal/

一、一眼看全仓库

multica/
├─ server/            Go 后端（HTTP + WebSocket + daemon + CLI）
│  ├─ cmd/            可执行入口：server / multica / migrate / maintenance / backfill_*
│  ├─ internal/       业务实现（43 个子包）
│  ├─ pkg/            可复用底层能力（14 个子包）
│  └─ migrations/     数据库迁移（589 组 up/down）
├─ packages/          前端共享包
│  ├─ core/           无界面逻辑：API 客户端、Query hooks、Zustand store
│  ├─ ui/             UI 原语与样式
│  ├─ views/          Web 与桌面端共用的页面与业务组件
│  ├─ plugin-sdk/     插件开发包
│  └─ tsconfig/ eslint-config/
└─ apps/
   ├─ web/            Next.js 路由与 Web 专属 UI
   ├─ desktop/        Electron 外壳与桌面专属状态
   ├─ mobile/         Expo / React Native（独立一套）
   ├─ docs/           Fumadocs 文档站
   └─ ui-lab/         组件实验室

二、前端：一条单向依赖线

AGENTS.md 把这条规则写成了表格里的一句话，值得逐字读：

源码原话

Dependency direction is views -> core + ui; core and ui remain independent.（AGENTS.md · Sharing Rules and Package Boundaries）

翻译成人话，三条禁令：

包能做绝对不能做
core/ API 客户端、TanStack Query hooks、共享 Zustand store、类型与校验 不引入 UI 库、react-dom、localStorage、process.env
ui/ 按钮、对话框这类 UI 原语与共享样式 不写业务逻辑；不许 import @multica/core
views/ 页面与业务组件（Web 与桌面共用） 不定义 store；不用 next/*、react-router-dom
关键事实

想判断"这个功能该放哪一层"，问一个问题：它需要知道"当前在哪个平台"吗？

  • 不需要 → 放 core/ 或 views/，Web 和桌面端同时受益。
  • 需要（Next.js 的 router、Electron 的窗口）→ 留在 apps/web 或 apps/desktop，通过适配器（Adapter）把平台能力"注入"到共享层。

所以你会看到 views/ 里用 useNavigation()、<AppLink> 这种抽象，而不是直接 router.push()。真正的跳转实现由各个 app 提供——这就是"依赖倒置"在前端的样子。

类比

你熟悉 PL/SQL 里的分层习惯：业务包不该直接读表名，而该调用封装好的数据访问过程。前端这三层是同一个思路——views 是业务包，core 是数据访问层，ui 是纯工具包。

区别在于：PL/SQL 靠命名约定，这里靠构建工具（ESLint + tsconfig references）强制。写错 import 直接报错。

mobile 为什么分家

apps/mobile 只复用 core 的类型与纯函数，UI、状态、hooks、i18n、构建、发版全部自己一套。原因不神秘：React Native 的渲染与 Next.js 完全不同，强行共用视图层只会两头受限。

三、后端：cmd / internal / pkg 三分

目录含义里面的东西
server/cmd/可执行入口（Go 惯例）server（HTTP 服务）、multica（CLI + daemon）、migrate、maintenance，以及 4 个一次性数据回填程序
server/internal/业务实现，不可被外部仓库 importhandler、service、middleware、daemon、realtime、daemonws、scheduler、integrations 等 43 个包
server/pkg/可复用的底层能力db（sqlc 生成物）、protocol（事件常量）、agent（CLI 适配层）、plugincontract、taskfailure

internal 这个名字不是随便起的：这是 Go 语言的硬机制——放在 internal/ 下的包，只有同一模块内部能 import。它把"这是我的私事"变成了编译器级别的约束。

小心

读 Go 代码时最容易被这个坑住：internal/ 下的东西，你在自己的外部项目里 import 不了，即使它长得像公共库。要复用的能力，作者才放在 pkg/。

顺带记住几个读代码的锚点（后面每一课都会用到）：

  • 全部 HTTP 路由 → server/cmd/server/router.go
  • 中间件 → server/internal/middleware/
  • Run 的业务主线 → server/internal/service/task.go
  • 手写 SQL → server/pkg/db/queries/；生成物 → server/pkg/db/generated/

六、检索练习

1. 你在 packages/ui/components/ui/button.tsx 里想 import 一个来自 @multica/core 的枚举，会怎样？

2. 你想在自己的独立项目里 import multica/server/internal/service，为什么不行？

3. 一个 Web 与桌面端共用的页面里需要"跳转到某个 Issue"，正确做法是？

不看上文，凭记忆说出：core、ui、views 各自"不许做什么"。

  • core：不许有 UI 库、react-dom、localStorage、process.env（要持久化就走 StorageAdapter）。
  • ui：不许有业务逻辑，也不许 import @multica/core。
  • views：不许定义 store，不许用 next/* 或 react-router-dom。

共同目的只有一个：让 Web 与桌面端能共用同一份业务代码，同时把平台差异逼到适配器那一层。
