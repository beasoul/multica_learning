Lesson 11

权限与安全：把三层边界分清

"安全"这个词在这个项目里被拆成了三个互不相同的问题：你是谁（认证）、你能做什么（授权）、Agent 能碰到你机器上的什么（执行隔离）。第三层的答案可能会让你意外——但它是官方文档里写得最清楚的一节。

约 40 分钟 对应图表：08 权限校验链 对应源码：apps/docs/content/docs/security-model.zh.mdx · members-roles.zh.mdx · internal/middleware/

一、三层边界，三个问题

层要回答的问题主要机制
认证你是谁？会话 Cookie / PAT / daemon 令牌 / 运行令牌（第 6 课）
授权你能在这个工作区做什么？路由级角色中间件 + workspace_id 作用域
执行隔离Agent 进程能碰到你机器上的什么？几乎没有机制——这是刻意留给外部的

第三层是这一课的重点，也是大多数教程会含糊过去的地方。我们把它放在最后单独讲。

二、授权：三种角色，一张表

官方文档 members-roles.zh.mdx 直接给了一张权限矩阵，照抄如下：

操作owneradminmember
查看工作区并参与日常协作✓✓✓
修改工作区设置✓✓—
邀请 admin 或 member✓✓—
调整或移除 admin、member✓✓—
授予、收回或移除 owner✓——
删除工作区✓——

这张表在代码里的落地方式，第 4 课已经见过——它就是一个路由分组的事：

// member 组
r.Use(middleware.RequireWorkspaceMemberFromURL(queries, "id"))

// owner/admin 组
r.Use(middleware.RequireWorkspaceRoleFromURL(queries, "id", "owner", "admin"))
关键事实

注意这两个中间件的命名：...FromURL。权限判断用的工作区 ID 是从 URL 路径里取的，不是从请求头或请求体里取的。

这是个有意的选择：路径是路由匹配的一部分，无法被客户端"顺便"改掉来绕过校验。

作用域：每个查询都要带工作区

AGENTS.md 里那条规定很短但很硬：

源码原话

Workspace-scoped queries filter by workspace_id; membership gates access and X-Workspace-ID selects the workspace.

拆开看是三件事：成员资格决定能不能进（授权中间件）、X-Workspace-ID 决定进哪一个（上下文选择）、SQL 里必须 WHERE workspace_id = ...（数据隔离）。第三件事是最容易被漏的——漏一个，就是跨租户数据泄露。

类比

这三件事在 Oracle 里对应的是：VPD / RLS 策略（行级自动过滤）+ 应用上下文（当前租户）。区别是 Multica 没用数据库层的行级安全，而是把它写在应用代码的每个 SQL 里。

代价很清楚：漏写一个 WHERE 就没有兜底。收益是查询可以按工作区做深度优化（还记得第 10 课那个"先按工作区收窄候选集"的检索策略吗？就是靠这个前提）。

三、认证层的其余零件

除了四种令牌，server/internal/middleware/ 里还有这些防线：

文件作用
auth.go主认证：Cookie / PAT / 云端校验
daemon_auth.godaemon 通道专用认证
plugin_auth.go + plugin_ratelimit.go插件的独立身份与限流（第 13 课）
ratelimit.go公开接口限流（登录、注册等）
session_renewal.go会话续期
csp.go内容安全策略响应头
cloudfront.goCDN 签名（附件下载等）
owner_lookup.go资源归属解析

另一个值得注意的细节藏在 router.go 的注释里：附件下载接口有一个"能力式"（capability）的公开路径，因为原生下载（Electron 的 webContents.downloadURL、跨站 <img>）既不携带 Authorization 也不带 Cookie。它的凭据是 URL 里那串短期、单文件的签名，而这串签名只在已认证的 GET /api/attachments/{id} 通过成员校验之后才会签发。

这是个很典型的取舍：为了让原生下载能用，必须开一个无认证入口；于是把安全责任转移到"签发环节"——能拿到签名就说明你已经被校验过了。

四、执行隔离：官方最诚实的一节

现在讲最要紧的一层。security-model.zh.mdx 的标题就叫《安全模型》，它的第一句结论是：

必须知道

边界是运行 daemon 的那个操作系统用户。默认情况下，每次执行拥有该用户的全部权限：它能读写的文件，运行都能读写；它的凭据，运行都能用；网络访问不受限制。

官方原文：Multica 不对文件系统沙箱作任何保证……请把每一次运行都当作无沙箱来对待，并把边界放在守护进程之外。

为什么不做沙箱？文档给的理由不是"没时间"，而是一个技术判断：

  1. Agent 需要装依赖、跑构建、用你的云 CLI——这些工具都假设自己面对一个正常的 home 目录。不完整的沙箱会让它们以极难排查的方式坏掉（报"未登录"、悄悄用错账号）。
  2. 更关键的是它挡不住真正要紧的事：只限制写入的沙箱，无法阻止运行读取凭据并通过网络发出去。

所以结论是："Multica 不假装自己是边界。请在它外面加一层。"

官方推荐的三种由轻到重的部署方式

方式做法代价
专用 Unix 用户建一个 multica 用户，只给它需要的仓库与凭据，用它运行 daemon最轻，自己的账号完全不受影响
容器容器里跑 daemon，只挂载需要的目录和密钥需要容器化
虚拟机隔离最彻底要多一台机器

无论选哪种，都要遵守一条原则：把该环境里可触达的凭据视为"Agent 可能会用到的凭据"——token 权限尽量收窄，优先用专用部署密钥而不是你的个人 SSH 私钥，别把无关的生产凭据留在那个 home 目录里。

哪些"隔离"是真的，哪些只是便利性

项目真实作用
每次运行独立工作目录（~/multica_workspaces/）并发运行不在同一份 checkout 上打架
每次运行独立的 Agent 状态（如运行级 CODEX_HOME）不污染你本机的 ~/.codex/
运行级 API token（mat_）运行无法通过 Multica API 冒充你或别的 Agent

文档把这三条明确归类为"便利性与影响面收敛，不是用来防御主动逃逸的安全边界"。这个区分很值得学：它避免了"我们做了沙箱所以安全"这类误导性表述。

小心

还有两条"不构成边界"的东西，容易被误解：

  • Agent CLI 自带的沙箱与审批设置：Multica 以无人值守方式运行，审批请求被自动应答；默认路径下沙箱关闭（Codex 用 danger-full-access，Claude Code 用 --permission-mode bypassPermissions）。唯一例外是 Windows 上你显式开启了 Codex 原生沙箱。
  • 你的 HOME 目录结构：运行继承 daemon 用户真实的 HOME 与 XDG_*——正因如此 gh、aws、kubectl 在运行内行为和在你 shell 里一致；同时也意味着那个 home 下的一切都可触达。

自查：这一条命令

multica daemon logs --lines 200 | grep "codex sandbox"

运行以无沙箱方式启动时，daemon 会记 warn 级日志。想确认 Codex 的实际生效配置，看该运行 CODEX_HOME 下 config.toml 里被这两个标记包住的托管块：

# BEGIN multica-managed
...
# END multica-managed

六、检索练习

1. 关于"Agent 能碰到你机器上的什么"，官方立场是？

2. 想知道"删除工作区"需要什么角色，最快的判断方法是？

3. 为什么授权中间件叫 RequireWorkspaceRoleFromURL，要从 URL 取工作区 ID？

不看上文，说出安全的三层，以及每层的机制或结论。

  1. 认证（你是谁）：会话 Cookie / PAT（mul_）/ daemon 令牌（mdt_）/ 运行令牌（mat_），逐级收窄。
  2. 授权（你能做什么）：owner / admin / member 三角色，靠路由分组里的角色中间件声明；所有查询必须按 workspace_id 过滤，成员资格把门，X-Workspace-ID 选工作区。
  3. 执行隔离（Agent 能碰到什么）：边界就是运行 daemon 的那个 OS 用户；Multica 不做文件系统沙箱，官方要求你在外面加一层（专用用户 / 容器 / VM），并假定该 home 下的一切凭据都可能被用到。

最容易误判的是第三层：工作目录隔离、运行级 token 这些是"影响面收敛"，不是安全边界。
