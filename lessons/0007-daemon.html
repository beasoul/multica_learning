Lesson 07

daemon：那台真正跑活的机器

前面几课的"daemon"一直是个黑盒。这一课把它拆开：它怎么启动、怎么知道有活、怎么抢到活、怎么把 Agent 拉起来、以及它如何防止"任务永远卡在 running"。

约 40 分钟 对应图表：05 daemon 唤醒与领取 Run 流程 对应源码：server/internal/daemon/{daemon,config,client}.go · internal/handler/daemon.go

一、它只做三件事

职责具体动作
登记能力扫描本机装了哪些受支持的 CLI，把每个"机器 + provider"注册成一个 Runtime 上报服务端
领取任务等通知 + 定时轮询；抢到一条 Run 就准备好目录和凭据
执行并汇报spawn CLI 进程，把进度/消息/用量回传，最后报完成或失败

记住一点：daemon 不写数据库（第 5 课），也不碰模型（第 1 课）。它是个"本机执行代理"。

二、启动序列

源码 daemon.go 的 Run() 方法就是启动全流程，顺序有讲究：

1. 先绑健康检查端口（默认 19514）
   └─ 端口起不来，说明本机已经有一个 daemon 在跑 → 立即退出，不打架
2. 加载配置（令牌从 CLI 配置里读）
3. 续期 PAT → 初始工作区同步
   └─ 这一步要 exec 每个已配置的 agent 拿版本号；冷缓存时约 20 秒
4. 注册 Runtime
5. 开始服务：健康检查 + 心跳 + 轮询/WebSocket 领取循环
关键事实

/health 的存活（liveness）和就绪（readiness）是分开报的：端口在第 1 步就起来了（所以 daemon start 不会一直 connection refused），但状态保持 "starting"，直到第 3 步完成才转 "running"。

这个设计防止"preflight 慢或失败"被误报成"daemon 已启动、准备就绪"。

三、两条拿活的路：通知 + 轮询

daemon 怎么知道"有活了"？两条路并行，缺一不可：

路径机制默认节奏
推送 daemon 与服务端保持一条 WebSocket（/api/daemon/ws），服务端发现你这个工作区有可领的任务就通知 即时
轮询 daemon 定时主动查询"有没有我能干的" MULTICA_DAEMON_POLL_INTERVAL=30 秒

还有一个更慢的兜底节奏 MULTICA_DAEMON_WS_CLAIM_POLL_INTERVAL=3 分钟，用于 WebSocket 明明连着但没收到通知的情况。

类比

这就是经典的"推 + 拉双保险"。推送省延迟，轮询保正确性——因为推送会丢（网络抖动、服务端重启、进程刚好在忙别的）。

和 Oracle 无关但思路一致：DBMS_SCHEDULER 的 job 到点由调度器主动启动（推），而你写个脚本每 30 秒查一次 DBA_SCHEDULER_JOB_RUN_DETAILS 看有没有结果（拉）。两个都不能少。

四、claim：为什么必须是"抢"

领取的接口是 POST /api/daemon/tasks/claim。关键在于：同一台机器、甚至多台机器上的多个 daemon 可能同时看到同一条 queued 的 Run。

服务端用一次数据库事务把它从 queued 改成 dispatched——改成功了才是你的。这叫做"原子认领"（claim），它保证一条 Run 只会被一个 daemon 接走，不会重复执行。

小心

如果你在排查时看到同一条 Run 出现"两个 daemon 都以为自己在跑"的日志，那不是正常设计——正常情况下一方会拿不到 claim。这类问题要去查事务与唯一约束，而不是查 daemon。

五、准备执行：目录是第一等公民

领到活之后，daemon 要做三件事才敢启动 Agent：

  1. 解析 Agent 配置：这个 Agent 用哪个 provider、带什么参数、挂哪些 Skill。
  2. 找到 CLI 可执行文件：本机该 provider 装在哪。这里有一整套"自愈"逻辑——如果路径变了、旧路径失效了，daemon 会重新探测并修正（源码里的 healAgentPath / adoptAgentPath）。
  3. 准备本地工作目录：默认落在 $HOME/multica_workspaces，可用 MULTICA_WORKSPACES_ROOT 改。目录归属与任务隔离都在这层处理。

第 3 步就是第 5 课那个 waiting_local_directory 状态的来源：同一个目录被另一条 Run 占着，daemon 就"停车"等，而不是硬上。

六、spawn：进程是它拉起来的

真正的执行是一句 spawn。daemon 把第 6 课那组环境变量塞进去：

MULTICA_TOKEN        = <mat_ 一次性运行令牌>
MULTICA_TASK_ID      = <这次 Run 的 ID>
MULTICA_AGENT_ID     = <哪个 Agent>
MULTICA_WORKSPACE_ID = <哪个工作区>
MULTICA_TASK_SLOT    = <并发槽位号>
MULTICA_SERVER_URL / MULTICA_DAEMON_PORT / TMPDIR ...

MULTICA_TASK_SLOT 是并发槽位。默认一台机器的并发上限是 MULTICA_DAEMON_MAX_CONCURRENT_TASKS=20——所以你会看到同一个 Agent 配置在界面上出现多个并行实例。

七、看门狗：防止"永远 running"

Agent CLI 是外部程序，它可能挂住、可能沉默、可能死循环。如果 daemon 不管，那条 Run 会永远停在 running。于是有了一组看门狗：

看门狗默认值管什么
MULTICA_DAEMON_HEARTBEAT_INTERVAL15 秒定期告诉服务端"我还活着"；服务端据此判断 Runtime 是否在线
MULTICA_AGENT_IDLE_WATCHDOG2 小时长时间没有任何活动的任务，判定为卡死并收敛掉
MULTICA_AGENT_TIMEOUT0（不限）整条任务的硬超时；默认不限，因为编码任务可能很长
MULTICA_CODEX_SEMANTIC_INACTIVITY_TIMEOUT10 分钟针对 Codex 这种自带定时器的 CLI 的"语义不活跃"判定
MULTICA_OPENCODE_IDLE_WATCHDOG10 分钟OpenCode 的专属空闲判定

注意最后一列的分化：每个 provider 的超时策略可以不同，因为它们自己的行为模式不同。这就是"适配层"存在的理由（第 8 课会把 pkg/agent 拆开看）。

八、它还在后台自己维护什么

作业节奏作用
工作区同步首次 30 秒，常规 30 分钟把本机有哪些 agent、哪些仓库同步到服务端
垃圾回收每 2 小时清理任务工作目录（默认 TTL 24 小时）、孤儿目录（72 小时）、可再生的构建产物（node_modules、.next、.turbo）
自动更新检查每 6 小时向 GitHub 查有没有新版本 CLI
小心

GC 只清工作副本，不动你的源码仓库。但它确实会删任务工作目录——不要把重要产物只放在 Multica 的工作目录里，该提交的提交，该回传的回传。

环境变量默认什么时候改

十、检索练习

1. daemon 已经通过 WebSocket 收到任务通知，为什么还要定时轮询？

2. daemon 领到一条 Run，但目标本地目录正被另一条 Run 占用，它会？

3. 为什么需要 MULTICA_AGENT_IDLE_WATCHDOG 这类看门狗？

不看上文，按顺序写出 daemon 从"知道有活"到"Agent 进程跑起来"的全部步骤。

  1. 收到服务端推送（/api/daemon/ws）或轮询发现可领任务（30 秒一轮兜底）。
  2. POST /api/daemon/tasks/claim 原子认领；服务端把 queued 改成 dispatched 并签发 mat_ 令牌。
  3. 解析 Agent 配置（provider、参数、Skill）。
  4. 定位本机 CLI 可执行文件（路径失效会自愈修正）。
  5. 准备本地工作目录；被占用则上报 waiting_local_directory 等待。
  6. POST .../start 声明开始 → running。
  7. spawn CLI 进程，注入 MULTICA_* 环境变量与 mat_ 令牌、分配并发槽位。
  8. 执行期间持续回传进度/消息/用量；看门狗监控空闲超时。
  9. 结束时报 complete 或 fail。
